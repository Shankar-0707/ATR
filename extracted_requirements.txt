1. Project Overview
You are building an AI Task Runner — a SaaS-style platform where users submit long-running AI tasks (summarise a PDF, transcribe audio, generate an image, translate a document, analyse sentiment in a CSV) and receive results asynchronously. The system processes tasks in the background using a Redis-backed job queue so the API never blocks and the user never waits.
This is not a tutorial project. It is a production-grade system that replicates the architecture used by real companies (Cloudinary, Remove.bg, AssemblyAI) and is designed specifically to demonstrate deep knowledge of distributed systems, Redis data structures, async processing, and full-stack ownership.
1.1 The core problem this solves
OpenAI API calls take 10–30 seconds. Whisper transcription can take 60–90 seconds for long audio. You cannot make a user wait for an HTTP response that long — browsers time out, servers crash under load, and the UX is broken. The job queue solves this: the API responds in milliseconds, the heavy work happens in a background worker process, and the user gets a live status update when results are ready.

2.2 Why Redis specifically — what you will learn
Redis is not just a cache here. You will use four distinct data structures, each for a different purpose:
Redis feature
How you use it in this project
Sorted Sets (ZADD / ZRANK)
BullMQ stores job queues as sorted sets. Score = priority. ZRANGEBYSCORE fetches next job. You learn why sorted sets are O(log N) and perfect for priority.
Streams + Consumer Groups
BullMQ v2 uses Streams for at-least-once delivery. If a worker crashes, the job is reclaimed. You learn fault tolerance at the data-structure level.
Pub/Sub (PUBLISH / SUBSCRIBE)
Workers publish job state changes. API server subscribes and forwards to dashboard via Socket.io. You learn event-driven architecture.
Hashes (HSET / HGET)
Full job payload, result, and error are stored as Redis Hashes. Sorted sets hold just the IDs. You learn data partitioning.
Atomic counters (INCR / INCRBYFLOAT)
Rate limiting (jobs/day per user) and cost tracking (tokens spent) use atomic Redis counters. No race conditions, no DB queries on hot paths.
TTL / Expiry (EXPIRE / SET EX)
Deduplication: hash of uploaded file stored with 5-minute TTL. Job locks stored with 30-second TTL. You learn how expiry enables distributed coordination.

7. Redis Patterns — Implementation Details
These are the exact Redis operations you implement manually (not via BullMQ). Write each one yourself to actually learn Redis.
7.1 Plan-based rate limiting
// On every POST /api/jobs request:
const key = `user:jobs:count:${userId}:${todayDate}`;
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, 86400); // resets at midnight
const limit = user.plan === &quot;pro&quot; ? 100 : 5;
if (count &gt; limit) throw new Error(&quot;Daily job limit reached&quot;);
7.2 Job deduplication
// Before enqueuing — prevents charging user twice for same file:
const fileHash = crypto.createHash(&quot;sha256&quot;).update(fileBuffer).digest(&quot;hex&quot;);
const dupKey = `dedup:${userId}:${fileHash}`;
const existing = await redis.get(dupKey);
if (existing) return { jobId: existing, duplicate: true };
await redis.set(dupKey, newJobId, &quot;EX&quot;, 300); // 5 min TTL
7.3 Cost tracking (atomic float increment)
// After each completed AI job in the worker:
const tokenCost = (promptTokens + completionTokens) / 1000 * 0.002;
const costKey = `user:cost:${userId}:${yearMonth}`;
await redis.incrbyfloat(costKey, tokenCost);
await redis.expire(costKey, 60 * 60 * 24 * 35); // keep for 35 days
7.4 Live status via pub/sub
// In worker — after every state change:
await redis.publish(&quot;job:updates&quot;, JSON.stringify({
  jobId, userId, status, progress, result
}));
// In API server — subscribe once on startup:
subscriber.subscribe(&quot;job:updates&quot;, (message) =&gt; {
  const data = JSON.parse(message);
  io.to(`user:${data.userId}`).emit(&quot;job:update&quot;, data);
});

Your interview answer
&quot;I built an AI Task Runner — a platform where users submit long-running AI jobs like summarising
documents, transcribing audio, and generating images, and receive results asynchronously.
The core problem was that OpenAI calls take 10-30 seconds. You cannot block an HTTP request
that long. I used BullMQ on top of Redis to queue jobs and process them in separate worker
processes. The API responds in milliseconds and the worker does the heavy lifting.
I used Redis sorted sets for priority queues — Pro users get priority 10, free users get

using content hash keys, and real-time cost tracking using INCRBYFLOAT. None of those
hit Postgres — they are all atomic Redis operations on hot paths.
The whole system is horizontally scalable — you add capacity by deploying more worker
containers pointed at the same Redis instance. I deployed it on Railway with separate
API and worker services.&quot;
